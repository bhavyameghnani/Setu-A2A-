# Decisions

Record of choices made where BUILD_SPEC.md was ambiguous or silent.

## Phase 0
1. **uv installed via `pip install --user uv`.** Python 3.12 is fetched by uv (system Python is 3.14); `requires-python` is pinned to `>=3.12,<3.13`.
2. **Spec revised mid-phase** to drop Docker and Redis. I deleted the Compose file and Dockerfiles I had first written and reworked Phase 0 to the new spec.
3. **Postgres 16 installed with `brew install postgresql@16`** and started with `brew services start` (it restarts at login; stop with `brew services stop postgresql@16`). It is keg-only, so the Makefile prepends its bin directory to PATH.
4. **Dependencies:** fastapi, uvicorn, pydantic-settings, structlog, SQLAlchemy 2 (async), asyncpg, Alembic, plus dev tools. SQLAlchemy/asyncpg/Alembic are needed now because `make db-migrate` and the throwaway-database fixture must work. a2a-sdk, PyJWT, argon2 and httpx (runtime) wait for the phase that uses them.
5. **Settings use unprefixed env names** (`DATABASE_URL`, `LOG_LEVEL`, `APP_ENV`), matching the spec's `DATABASE_URL`. `.env` is read from the repo root or `server/`; real env vars win.
6. **Default DB URL** is `postgresql+asyncpg://localhost:5432/setu` with no user, so Postgres uses the OS user (Homebrew default). Set `DATABASE_URL` for Neon or other hosts.
7. **Alembic is initialized (async template) with zero migrations.** `make db-migrate` is a no-op until Phase 1 adds the first forward-only migration. `env.py` takes the URL from app settings.
8. **Test database:** a session fixture creates `setu_test_<id>` and drops it at session end, then points `DATABASE_URL` at it. It connects through the `postgres` maintenance database, so the role needs CREATEDB.
9. **`make db-create` is idempotent** (skips if the database exists). `DB_NAME` defaults to `setu`.
10. **`scripts/dev.sh`** loads `.env`, checks Postgres is reachable (with a hint on failure), then runs uvicorn `--reload` on 8000 and Vite on 5173, cleaning up both on exit. It runs `npm install` if `web/node_modules` is missing.
11. **`/healthz` is liveness only**; it does not touch the database. Readiness comes with Phase 1.
12. **Stub modules are empty files** for every path in spec section 6.
13. **Web is a bare Vite + React + TS + Tailwind + TanStack Query shell** with no UI (Phase 9).
14. **mypy** runs on `app`, strict only on `app.core.*` and `app.a2a.*`. Ruff: E, F, I, UP, B, ASYNC, line length 100.
15. **No git repo was created** and nothing was committed.
16. **Starlette `TestClient` deprecation warning** about `httpx2` is tolerated for now.

## Phase 1
17. **Per-room `seq` via `rooms.last_seq`** (extra column, not in spec section 7). `UPDATE rooms SET last_seq = last_seq + 1 RETURNING` in the same transaction as the insert takes the room row lock, so seq is gap-free and commits in order. Cost: senders to one room serialize, which is fine for MVP.
18. **No auth yet.** Requests carry `sender_id` / `created_by` / `participant_id` explicitly. Phase 2 replaces these with the authenticated caller. Until then the API must not be exposed beyond localhost.
19. **Only the Phase 1 tables exist** (orgs, departments, participants, rooms, room_members, messages). `messages.task_id`, `trace_id`, `span_id`, `delegation_chain_id` are plain nullable columns; FKs come with their tables.
20. **Enums are TEXT + CHECK constraints**, not Postgres enum types, so later migrations can extend them easily.
21. **Posting requires room membership** (403 otherwise) and observers cannot send. Department-based visibility is Phase 2. Adding a participant from another org is rejected (cross-org denied).
22. **UUIDv7 ids** come from a small in-repo generator (`app/db/ids.py`) because Python 3.12 has no `uuid.uuid7`.
23. **Fan-out:** one shared asyncpg LISTEN connection on channel `setu_messages`; payload is `room_id:seq` only. Each WebSocket subscribes before its first fetch, then fetches rows by `seq`, so replay and live share one code path. A 5 s poll fallback covers a missed NOTIFY, and the listener reconnects with backoff and wakes everyone to catch up.
24. **WebSocket protocol:** `/v1/ws/rooms/{room_id}?participant_id=&after_seq=`. Server sends `{"type":"message","message":{...}}`; client sends `{"type":"send","kind","body","mentions","reply_to"}`. Sent messages return through the same stream, so the sender sees the canonical seq. Non-members are closed with code 4403.
25. **Delivery is at-least-once in principle; clients dedupe by message id.** No client-supplied idempotency key yet (revisit with A2A message-id dedupe in Phase 4).
26. **`/healthz` now checks the database** and returns 503 `{"status":"degraded"}` when it is down. The app still boots without Postgres.
27. **`create_app(database_url)` factory** so tests build an app against the throwaway database. Tests apply the real Alembic migration (no `create_all`).
28. **Migration `0001` was autogenerated and kept as generated**; ruff ignores line length and style in `alembic/versions`.

## Phase 2
29. **First admin is created by a CLI**, not an open endpoint: `make bootstrap ORG=... DEPT=... SLUG=... EMAIL=... NAME=...` (password from `ADMIN_PASSWORD` or a prompt). It creates the org, a first department and a human with `org_admin` + `dept_admin`. `POST /v1/orgs` was removed. Everything else goes through the authenticated API.
30. **Auth model:** humans log in with email + password (`POST /v1/auth/login`) and get an HS256 JWT (default 60 min, no refresh token yet). Agents and services use API keys (`X-API-Key`, or as a bearer token). Roles and status are re-read from the database on every request, so a role change or deactivation applies immediately; a JWT carries only the participant id.
31. **API keys** look like `stu_<8 hex prefix>_<48 hex secret>`. The prefix is stored in clear to find the row; the full key is stored only as an argon2 hash and returned once at creation. Revocation is immediate. Argon2 verification on every request costs some milliseconds; add a short-lived cache if it ever shows up in profiles.
32. **Scopes on API keys:** `rooms:read`, `rooms:write` (create rooms, manage members/access), `messages:send`. Default for a new key is read + send. Human sessions are unrestricted. These are the same scope strings Phase 5 delegation will narrow.
33. **`JWT_SECRET`** is required when `APP_ENV` is not `dev`; in dev a well-known placeholder is used so local setup needs no steps. It must be a real secret anywhere shared.
34. **Visibility rules** (`app/db/access.py`, used by REST and WebSocket): a participant reads a room if it is a member, or it is a human whose department has an access row. It posts if it is a non-observer member, or a human whose department has `participate` (and it is not an observer member). Agents never get access through department rows, only by membership. Rooms in another org are invisible.
35. **404, not 403, for rooms you cannot see**, so existence is not leaked. 403 is used only when you can see the room but lack permission (read-only department posting, non-manager changing access).
36. **Access rows on creation:** `private` rooms get none (member-only); `department` and `cross_department` rooms give the owning department `participate`. `department` rooms accept grants only for the owning department; `private` rooms accept none. Grants and revokes are `PUT/DELETE /v1/rooms/{id}/access`.
37. **Managers:** a room owner, a `dept_admin` of the owning department, or an `org_admin`. Managers can see a room's existence and change its members and access, but this does not give them message read access; `org_admin` does not bypass visibility. They could add themselves as a member, which is exactly the kind of action Phase 5 audit should record.
38. **`auditor` role** is stored and assignable (org_admin only) but has no effect yet; trace/audit visibility arrives with those phases.
39. **One department per human.** The spec's "optionally others" is deferred; cross-department access is expressed through room access rows.
40. **Department admins** can create humans and agents and mint API keys only in their own department, and can grant only `dept_member`/`dept_admin`. Only `org_admin` can create departments or grant `org_admin`/`auditor`.
41. **Agent participants** are created with `POST /v1/participants` for now (kind `agent`). Phase 4 adds registration by Agent Card URL; Phase 8's SDK agents connect with an API key and the WebSocket. This is the path your Compliance/Finance FastAPI agents will use.
42. **WebSocket credentials** are accepted as headers or as `?token=` / `?api_key=` query params (browsers cannot set headers on WebSockets). Query strings may appear in logs; agents and the SDK should use headers. Post permission is re-checked on every send; read access is checked at connect only, so removing access does not yet kick an open socket.
43. **Emails** are lowercased and validated with a simple regex (no `email-validator` dependency). Passwords need 10+ characters. There is no login rate limiting or lockout yet.

## Phase 3
44. **Addressing is decided once, at send time**, by `core/routing.py` (pure; no DB, no network, no LLM, with an AST test that forbids those imports). The result is stored on `messages.addressed` (uuid[]) and as `message_status` rows (`pending`), so later membership or subscription changes never rewrite history.
45. **Who can be addressed:** room members who are not observers and not the sender. Mentions of non-members or observers are ignored, not errors. `activity` and `system` messages address nobody.
46. **Subscriptions** (`kind` and/or `skill`, `''` = any) are a new table because the spec's rule 9.2 needs somewhere to hold them. A message's skills come from `body.skill` (string) and/or `body.skills` (list). Only non-observer members can subscribe.
47. **Delivery status machine** (`core/lifecycle.py`): `pending -> acked -> completed | failed`; `pending` may jump straight to a terminal state; repeating the current status is a no-op; terminal states are final (409). Only addressed participants have a row, so anyone else gets 404.
48. **Cursors are explicit.** The server never advances a cursor on delivery, because delivered is not processed (at-least-once). Clients ack via `PUT /v1/rooms/{id}/cursor` or a WebSocket `{"type":"ack"}` frame. Cursors only move forward and cannot pass the room's last `seq`.
49. **WebSocket resume:** without `after_seq` the stream starts from the caller's cursor; an explicit `after_seq` overrides it. `GET /v1/rooms/{id}/inbox` lists addressed-but-unfinished messages as a second catch-up path.
50. **Snapshots** are written by a background loop (default every 300 s, `SNAPSHOT_INTERVAL_SECONDS=0` disables) once at least `SNAPSHOT_MIN_MESSAGES` (50) new messages exist. The default summary is a deterministic digest (counts by kind and sender, no message text). An LLM summarizer can replace it later, only in this job. `(room_id, up_to_seq)` is the key, so racing workers cannot double-write.
51. **Task assignee routing** is wired in Phase 4 once the `tasks` table exists; until then `assignee_id` was always `None`.

## Phase 4
52. **Plain httpx client, not the `a2a-sdk` client.** Setu needs per-agent version negotiation, a `traceparent` on every call, auth headers derived from the card, raw-event control and explicit retries, which are simpler over a thin JSON-RPC/SSE layer (`a2a/client.py`) with a per-version adapter (`a2a/versions.py`). `a2a-sdk[fastapi]` is a **dev dependency only**, used by the 1.0 reference agent in tests. The SDK server's dual-version support will be reused for the Phase 6 facade. Research notes: `docs/a2a-notes.md`.
53. **Version detection** reads the JSON-RPC entry in `supportedInterfaces` (1.0 card) or the top-level `url`/`protocolVersion` (0.3 card); an interface that advertises `0.x` is spoken to in the 0.3 dialect even inside a 1.0-shaped card. Wire differences handled: method names, `TASK_STATE_*` vs lower-hyphen states, `kind`-tagged parts, event wrapping, `final` flag, and the `A2A-Version: 1.0` header (sent for 1.0 only).
54. **Only JSON-RPC over HTTP** (with SSE streaming) is supported. A card offering only gRPC or REST is rejected at registration (422). If the card says `streaming: false`, a blocking `SendMessage` is used and its final Task is mirrored.
55. **Card lookup:** a base URL, or a well-known path, tries `/.well-known/agent-card.json` then `/.well-known/agent.json`; any other URL is used as given. Registration is by admins of the owning department; the same card URL cannot be registered twice in an org.
56. **Credentials:** `{type: bearer, token}` or `{type: api_key, header, value}`, encrypted with Fernet (`ENCRYPTION_KEY`) into `agents.auth_config` as `{"v":1,"ct":...}` and never returned by any endpoint. As with `JWT_SECRET`, a public dev key is used only when `APP_ENV=dev`. A card that declares security schemes registered without credentials gets a warning, not an error.
57. **Endpoint secrecy (spec 8.5):** the public agent view (skills, versions, enabled) omits the card URL and real RPC URL. Only admins of the owning department see them (`AgentAdminOut`).
58. **SSRF guard** (`a2a/ssrf.py`): http(s) only, no URL credentials, and outside `APP_ENV=dev` every resolved address must be globally routable. Applied to the card URL, the card's RPC URL, and again before each call. Redirects are never followed. Known gap: a DNS-rebinding race between the check and the connection; closing it means pinning the resolved IP.
59. **Tasks are created inside the `task` message's transaction** (one per addressed, enabled `a2a_remote` agent), so a committed task message always has its task. A dispatcher claims `submitted` tasks (`FOR UPDATE SKIP LOCKED`, `claimed_at`), woken immediately after the message commits and otherwise polling every second, bounded by `A2A_MAX_CONCURRENT_TASKS` (20). `sdk` agents are addressed but not dispatched over A2A.
60. **Task messages:** a `task` body is `{text?, data?, skill?}` (or an explicit `parts` list) and becomes A2A parts. Replies are posted **as the assignee agent**, addressed to the requester, in the task's thread (`messages.task_id`): `task_update` per state change, `result` per artifact (on `lastChunk`, or at the end for chunked ones), `approval_request` for `input_required`. A message may carry `task_id` to join a thread (the assignee is then addressed without a mention); on a `task` message it names the parent task, and the trace id is inherited.
61. **Mapping choices:** room id is the A2A `contextId`; the A2A `messageId` is a UUIDv5 of the Setu task id, so every retry reuses it (idempotency); `traceparent` is sent as an HTTP header and mirrored in message metadata. `auth_required` is recorded as a state; the credential flow arrives with Phase 5.
62. **Failures are always visible.** Retries (default 2, per agent, exponential backoff from `A2A_RETRY_BACKOFF_SECONDS`) happen only for outages before any event arrived; 4xx responses and mid-stream failures fail immediately. A `-32009`/`-32601`/404-class mismatch triggers one card refresh and retry. Every failure ends as a `failed` task plus a `task_update` with `origin: "hub"` and the error. Per-agent `timeout_seconds` is the tolerated silence between stream chunks, not a total cap.
63. **Restart behaviour (single instance assumed):** at startup, tasks that were claimed but never finished are failed visibly ("the hub restarted"). Resuming them with `GetTask`/`SubscribeToTask` is a possible later improvement. Multi-instance deployments would need a lease instead.
64. **Cancel** (`POST /v1/tasks/{id}/cancel`, requester or room manager) calls A2A `CancelTask`, stops mirroring the stream, and marks the task `canceled` with a visible message. If the agent refuses, the task is left alone and the caller gets 502.
65. **Task state machine** (`core/lifecycle.py`): terminal states are final, nothing returns to `submitted`; an agent reporting an illegal transition is logged and ignored.
66. **`agents` table** also holds `sdk` agents: `POST /v1/participants` now creates its `agents` row, so one registry lists every agent. Extra columns beyond spec section 7: `a2a_version`, `a2a_rpc_url`, `streaming`, `card_hash`, `timeout_seconds`, `max_retries`; `tasks` gained `request_message_id`, `error`, `claimed_at`.
67. **Scheduled card refresh** runs hourly (`AGENT_CARD_REFRESH_SECONDS`, 0 disables); `POST /v1/agents/{id}/refresh` does it on demand and reports whether the card changed. Notifications for card changes arrive with Phase 7.
68. **Tests use in-process agents** routed by hostname through `HostRouter` (a test-only httpx transport): a 1.0 agent built with `a2a-sdk` and a hand-rolled 0.3 agent (`tests/a2a_agents.py`, written by a subagent against a contract I specified, then verified by the suite). The "contract tests against a reference agent" requirement is met for 1.0 and 0.3; testing against a *separately deployed* agent comes with the Phase 8 examples.

## Phase 5
69. **Policy rules are JSON documents parsed by `core/policy/engine.py::parse_rule`** (pure, shared by the API and the engine). Departments are referenced by id or `*` (no slugs). `topic_block` matches `body.skill`/`body.skills` against `topics`. Evaluation order: cross-org deny, `deny_talk`, `topic_block`, default-deny for cross-department unless an `allow_talk` matches, then `require_approval`, else allow. `allow_talk` is directional. Rules are evaluated for each *addressed* recipient, so unaddressed context messages are never policed.
70. **What is checked:** messages a participant initiates (`text`, `task`). Hub-posted replies (`task_update`, `result`, `approval_*`, `activity`, `system`) are exempt, since they answer an already authorized task. `require_approval` applies only to `task` messages (it needs a task to hold); on a `text` message it is treated as allow. Allows are audited for tasks only; denials are always audited.
71. **Denials are audited in their own commit.** `authorize_send` runs before anything is written, so it commits the audit event and then raises `ControlDenied` (REST 403 with the reason, WebSocket error frame with `denied: true`). Nothing is stored for a denied message.
72. **Default-deny changes existing behaviour:** any cross-department task or addressed message now needs an `allow_talk` rule. Test fixtures create one (`Acme.allow_talk`).
73. **Policy is re-evaluated at dispatch** (`control.authorize_call`), together with the delegation chain, because rules and grants change after a send. A deny ends the task `rejected` (visible `task_update` with `origin: "hub"`). A `require_approval` match with no approved approval holds the task even then.
74. **`approvals` table** (not in spec section 7) records who must decide and lets a held task resume. Two kinds: `policy` (gates a task before the agent is called) and `agent` (answers the agent's own `input_required`). `summary` is a deterministic template, no LLM. Approvers see the summary through `GET /v1/approvals` without needing read access to the room; the `approval_request` message in the room is for people who already have it.
75. **Held tasks sit in `input_required`** with no `claimed_at`, so the dispatcher (which only claims `submitted`) leaves them alone. Approving calls `lifecycle.release_gated`, the only way back to `submitted`, reserved for the hub. Denying ends the task `rejected`. Nobody can approve their own request; `org_admin` can decide any approval in the org.
76. **Agent questions** (`kind=agent`): the requester answers (or a dept admin of the requester's department; for agent requesters, a dept admin). Approve sends the `note` back to the agent as a follow-up A2A message on the *same* `taskId`/`contextId` (message id is a UUIDv5 of the task and approval, so retries dedupe); deny sends a best-effort `CancelTask` and marks the task `canceled`. `A2AClient.stream_message` gained `task_id` for this. Resumption is picked up by the dispatcher via `approvals.resumed_at`.
77. **Delegation scopes** are `*`, `skill:*` or `skill:<id>`. A task sent by an agent must carry `delegation_id` naming a grant the sender *holds* that covers `skill:<skill>` for each skill (or `skill:*` when it names none). Humans are the root of authority and need none. Grants only narrow: scopes must be a subset of the parent's, and a child must expire no later than a parent that expires (a child with no expiry under an expiring parent is refused). Revoking a grant ends everything below it, because the chain is checked end to end at use. `tasks.delegation_chain_id` and `messages.delegation_chain_id` hold the leaf grant id; `GET /v1/delegations/{id}/chain` returns leaf first, root human last.
78. **Delegation endpoints use API key scopes agents already have** (`messages:send` to create/revoke, `rooms:read` to read), rather than adding a new scope.
79. **Audit log:** `hash = sha256(prev_hash || canonical_json(event))` where the event includes org, seq, type, actor, payload and a microsecond UTC timestamp. Chain is per org, appended under a per-org advisory lock inside the caller's transaction. A trigger blocks UPDATE, DELETE and TRUNCATE; the table owner can disable the trigger, which is exactly what `POST /v1/audit/verify` is for. Known limit: truncating the *tail* of a chain is not detectable from the table alone (it would need an external anchor of the latest hash).
80. **Audit visibility:** `GET /v1/audit` and `POST /v1/audit/verify` are for `org_admin` and `auditor` (this gives `auditor` its first effect, decision 38). Policies are readable by both and writable by `org_admin` only. Audited events: policy changes, decisions, approvals, delegation create/revoke/deny, room member add (with `self_added`) and department access grant/revoke (decision 37).
81. **Deleting a policy** sets `approvals.policy_id` to null instead of blocking; the deletion is audited with the rule text.

## Phase 6
82. **Facade uses the `a2a-sdk` server** (now a runtime dependency; `uv.lock` needs regenerating with `uv lock`, since `uv` was not available here). `POST /a2a/{handle}` hands the request to the SDK's JSON-RPC routes with `enable_v0_3_compat=True`, so 1.0 and 0.3 callers share one endpoint. One SDK handler is cached per (caller, callee) pair: its task store is private to that caller, and tasks keep running after the request that started them (needed for `returnImmediately` and a later `CancelTask`).
83. **Everything needs a Setu credential**, cards included. Handles are only unique within an org, so an unauthenticated lookup is ambiguous; an unknown handle, a disabled agent and an `sdk`-transport agent all answer the same 404. Auth is the caller's API key (`X-API-Key` or bearer); starting a task needs `messages:send`, reading a card needs `rooms:read`.
84. **Proxied card** is built from an allow-list (name, description, version, modes, skills), not copied: the origin's provider, documentation and icon URLs are dropped. `/.well-known/agent-card.json` is 1.0-shaped and lists both a 1.0 and a 0.3 JSON-RPC interface at the Setu URL; `/.well-known/agent.json` is the 0.3 shape. The security scheme is an API-key header. `PUBLIC_URL` sets the base URL cards advertise (default: the request's).
85. **A call is a `task` message.** `contextId` must be the id of a room where the caller may post and the callee is a non-observer member; no rooms are created implicitly. Anything else is `InvalidParams` ("no such room for this caller" is used for both missing and invisible rooms). Skill and delegation come from `message.metadata.setu.skill` / `.delegation_id`. The body is the message parts plus `skill`, so policy, topic rules and delegation scopes apply exactly as for a UI task.
86. **Mapping at the edge:** the SDK fixes the wire task id before the executor runs, so the A2A task id is the SDK's and Setu keeps `(wire id -> Setu task, caller)` in memory; like the SDK's in-memory task store, it does not survive a restart (a `GetTask` after one is "not found"; the Setu task itself is unaffected). The first event carries `metadata.setu.trace_id`. Results are streamed as artifacts when Setu posts the `result` message; the closing state is sent only after its `task_update` has committed.
87. **Denials answer with a `rejected` task**, not a JSON-RPC error, carrying the reason (policy and delegation refusals are normal A2A outcomes; malformed requests are errors).
88. **Follow-up messages to an existing task are refused** through the facade. An `input_required` task is answered with `POST /v1/approvals/{id}/decide` (decision 76), by the human or department admin who owns the approval. Wiring A2A follow-ups to approvals is a possible later step.
89. **Cancel** (`CancelTask`) uses the same function as `POST /v1/tasks/{id}/cancel` (`a2a/cancel.py`): the requester or a room manager; the agent's refusal leaves the task alone. Only the caller that started a task can cancel it through the facade.
90. **Spans:** `id` is the 16-hex W3C span id (text), with extra columns `org_id`, `room_id` and `name`. A trace starts at a `task` message (new trace, or the parent task's, or the caller's `traceparent`); plain text messages are not traced. Per task message: `message` span (root or child), `delegation` span (agent senders only: chain leaf-first, root human, scopes, needed scopes), one `policy` span per addressed recipient (all decisions for tasks, denials for text), an `approval` span open until a human decides, and an `a2a_call` span covering Setu's call to the agent (closed with the task state it ended in and `duration_ms`). A denied send writes a `denied` message span as the root so the refusal is traceable even though no message exists. A resumed call (after an answer) adds a second `a2a_call` span. `tasks.span_id` holds the latest call span, so child work hangs off it.
91. **A -> B -> C needs no special support.** Setu sends B `traceparent` with the `a2a_call` span id; when B calls Setu's facade for C and forwards that header, C's `message` span becomes a child of the A->B call. Child tasks started from the room UI (`task_id` naming a parent) parent the same way. A malformed `traceparent` is ignored and starts a fresh trace instead of failing the call.
92. **Trace visibility:** a person sees only spans whose room they can read (membership or their department's access row); an auditor sees the whole trace in their org. The response says how many spans were hidden. A trace with nothing visible is a 404. An external caller's span (the parent of our first span) is not in our table, so our first span is shown as the root and keeps its `parent_span_id`.
93. **Addresses are scrubbed from failure texts** (`mapping.scrub`) before they are stored in task errors, messages or spans, and again in everything the facade emits. A `failed`/`rejected` text such as "blocked unsafe agent address: http://..." no longer contains the address; admins still see the real endpoint in the registry.
94. **Known limits:** facade task ids and handlers are in memory (single instance, like decision 63); the facade polls the database every 50 ms per open call instead of using LISTEN/NOTIFY; there is no gRPC or REST binding; push notifications are not offered (capabilities advertise streaming only).

## Phase 7
95. **The notification is the activity record; no extra `activity` messages are posted in rooms.** Spec 12 asks for activity messages made from templates for the humans of every involved department. Those humans often cannot read the room (decision 35), so the sentence is delivered as a `notifications` row. The room already carries `task_update`, `result` and `approval_*` messages for the same events, and adding a parallel `activity` message would double every task in the room and change message ordering for agents. The `activity` kind stays available for later.
96. **Templates are pure** (`core/notifications.py`): one sentence per event, built from display names, the skill (or the first 60 characters of the request) and a clipped detail. Events: `task.started|completed|failed|canceled|rejected|input_required`, `approval.requested|granted|denied`, `policy.denied`, `agent.registered`, `agent.card_changed`. Example: "Risk-Agent finished risk.score for olga. Result attached." No LLM; an LLM summary may later be attached by a background job (spec 12).
97. **Who is told** (`db/notifications.py`): every active human of each involved department, once per event. Task events: requester's and assignee's departments, plus the approver's department if the task needed sign-off. `approval.requested`: the approver department's holders of the required role (so a member who cannot decide is not asked), plus the requester's and assignee's departments. Approval outcomes: the same departments, except the person who decided. `policy.denied` (policy or delegation refusal): sender's and recipient's departments. Agent events: the owning department. `task.started` is sent once per task, not again when a call resumes after an answer. An agent's own question produces `task.input_required` (carrying the approval id), not a second `approval.requested`.
98. **A notification does not grant access.** A Risk person can be told about an Ops room task without being able to open the room. `actions` is computed when the notification is read: `open_room`, `reply`, `cancel_task` (task still live, and the person is the requester or a room manager), and `approval_id` (a pending approval this person may decide, which can be done from the inbox without room access, decision 74). If access changes later, the same notification gives different actions.
99. **Delivery.** Rows are written in the transaction of the event they report. Inbox: `GET /v1/notifications` (newest first, `unread_only`, `limit`, `before` paging by uuid7 id, `unread` is the total unread, not the page), `/unread-count`, `/{id}`, `POST /{id}/read` (idempotent), `POST /read-all`. Everything is private to the recipient (404 for anyone else) and for people only (403 for agents). Live push: `/v1/ws/notifications` (header or `?token=`), a Postgres NOTIFY on `setu_notifications` with `<recipient>:<id>` only, rows read from the database; without `after_id` only new notifications are pushed, with it everything newer is replayed first; a 5 s poll is the safety net, like rooms.
100. **Acting from the inbox:** reply = `POST /v1/notifications/{id}/reply`, a human `text` message in the room that joins the task's thread so its agent is addressed (decision 60); it re-checks room access and goes through policy like any send. Approve/deny = `POST /v1/approvals/{approval_id}/decide`; cancel = `POST /v1/tasks/{task_id}/cancel` (ids are in `actions`/`detail`). No new endpoints duplicate those rules.
101. **Known limits:** one row per human per event, so large departments multiply rows (no digest, mute or per-person preferences yet); no email; notifications are not retained or pruned; the card-change note lists added and removed skill ids only.

## Phase 8
102. **`setu-sdk` is its own package** (`sdk/python`, import name `setu_sdk`; hatch wheel, deps `httpx` and `websockets`). LangGraph and A2A serving are optional extras (`[langgraph]`, `[serve]`); the client and `Agent` import neither. The server's dev environment installs it editable with `langgraph` for tests and the demo, and `uv.lock` was regenerated (which also resolves decision 82's pending lock). `make lint` and `make typecheck` now cover `sdk/python` and `examples` (`mypy --strict` on the SDK and the demo).
103. **`SetuClient` is a thin wrapper over the existing REST and WebSocket API**, as one participant (an API key): `send`, `send_task`, `history`/`replay`, `cursor`/`ack`, `inbox`, `set_status`, `stream` (WebSocket; reconnects with exponential backoff and jitter and resumes from the last message it yielded), `task_for`/`subscribe_task`/`wait_task` (polling; waits through `input_required` by default because that is usually a human approving), `delegate`, `trace`. Errors are `SetuError(status, detail)`. "Join a room" is being a member (a room owner adds you); `Agent` joins every room it is a member of and notices new ones.
104. **`Agent` semantics.** `on_message` runs only for messages that name the agent in `addressed` and were not sent by it; the rest go to `on_context`. Each addressed message is marked `acked`, then `completed` (or `failed` if `on_message` raised), and the cursor is advanced after every message, so a crash resumes at the first unprocessed one. Delivery is at-least-once, so it dedupes by message id, and on (re)connect it skips replayed messages it already finished before a crash, using the room's `last_seq` and its inbox (addressed-but-unfinished) as the test. Cursor persistence is the hub's, not a local file (decision 48: the cursor is explicit and server-side).
105. **An SDK agent is also addressed by replies to its own tasks** (`task_update`, `result`, `approval_*` from the hub or from the agents it asked). They are not requests. `Agent.on_message` documents this and `LangGraphAgent` only runs the graph for `text` and `task` (`kinds=`). Found by the demo, where the Triage graph was being run on Risk's replies.
106. **LangGraph adapter: a graph run is a message-level task.** Each addressed request is one run (`thread_id` = the message id). A `task` request is answered with `task_update` (`origin: "sdk"`) and `result` messages that reply to it; a plain `text` request gets a text reply, including when the graph fails ("I could not do that. ..."). `progress=True` posts a `task_update` per graph step. Nodes reach Setu through `config["configurable"]["setu"]` (a `SetuContext`), and LangGraph passes `config` only to nodes whose parameter is annotated `RunnableConfig`. **Known gap:** tasks sent to an `sdk` agent are not `tasks` rows (decision 59), so they have no task state, notifications or trace spans of their own. A graph that needs those should be served with `a2a_serve` and registered by card URL.
107. **`a2a_serve`**: `build_a2a_app(handler, name=, url=, skills=)` serves an async callable (`A2ARequest -> str | dict | list of parts`) or, via `graph_handler(graph)`, a compiled graph, as an A2A agent on the `a2a-sdk` server: A2A 1.0 and 0.3 on one `/rpc` endpoint, a 1.0 card (listing both interfaces) and a 0.3 card, SSE streaming, optional bearer token, `req.progress(text)` for status updates, cancellation, and handler exceptions become a `failed` task carrying the message. Skill descriptions and tags default (to the name and the first id segment) because the A2A spec requires them. The result becomes the task's artifact: a str is a text part, a mapping a data part.
108. **Data parts are protobuf `Struct`s, so every number arrives as a float** (`83` becomes `83.0`). Consumers cast what they need as integers (the demo's Triage does).
109. **`EmbeddedServer`** (`a2a_serve`) is a uvicorn server that never touches process signal handlers, used by `serve()` and the demo. Several plain `uvicorn.Server`s started and stopped on the main thread leave the process holding a SIGTERM handler bound to a stopped server, and `sse-starlette` (A2A streaming) reads that handler to decide whether the server is shutting down, so every other server in the process then cuts its SSE streams after the first event. This broke unrelated tests until fixed; `test_embedded_servers_leave_process_signal_handlers_alone` guards it.
110. **Demo layout** (`examples/cross_department`, a package; run with `make demo`): Triage (Ops) is a LangGraph app run by the adapter; Risk is a native `a2a-sdk` server that calls Compliance through Setu's facade with the `traceparent` it received and the delegation Triage passed on; Compliance is a LangGraph graph served by `a2a_serve`. `seed.py` uses only the public API (the admin's department is Operations; it creates the rest, is safe to re-run because every run tags its own people, agents and room, and skips policies that already exist by name). The approval gate sits on the Ops -> Risk hop, not Risk -> Compliance, because the facade ends a call at `input_required` (decision 88): a gate on a call made *through* the facade would end the caller's call before the human decides. `--no-approval` skips the gate.
111. **Demo credentials:** demo people share the password `demo-password-123`, for a dev setup only. The Risk agent's API key (to call Compliance through Setu) exists only after Setu knows the agent, so the launcher serves Risk first, registers it, and then hands the key to the running executor.

## Phase 9
112. **Stack as decided (spec 5), plus build tooling only.** React 18, Vite 5, TypeScript, Tailwind 3, TanStack Query. No router or component library: routes are a 40-line hash router (`lib/router.ts`; links are plain `<a href>` and back/forward work). Dev dependencies added: `openapi-typescript` (types), `vitest@2` (pinned: Vitest 3+ needs Vite 6, and the bundler was not changed), `@types/node`. Playwright (Python) was added to the server's dev group for the browser tests.
113. **Same-origin through a proxy.** The browser talks to `/v1/...` on its own origin; Vite's dev and preview servers proxy it (and WebSockets) to `SETU_API`, so the server needs no CORS configuration and the `?token=` WebSocket credential (decision 42) never crosses origins. Production serving of `web/dist` behind the same reverse proxy as the API is the equivalent; no CORS middleware was added.
114. **Types come from the server.** `web/openapi.json` and `web/src/api/schema.d.ts` are generated (`make api-types`) from `app.openapi()` and committed; `make typecheck` runs `api-types-check`, which fails if they are stale. `src/api/types.ts` only gives the generated types friendly names. The A2A facade is not in the OpenAPI document (it is mounted as plain routes), so it has no web types; the UI does not call it.
115. **Auth.** The JWT is kept in `localStorage` (memory fallback if storage is blocked) and sent as a bearer token; any 401 clears it and returns to the sign-in page. It expires after `JWT_TTL_MINUTES` (default 60) and there is no refresh flow yet: the person signs in again. Login shows nothing department-specific until you are in; after that the header always shows your name, department badge and roles.
116. **What a page shows is what the server returned.** Nothing is filtered in the browser for security; the UI only decides what to *offer*. `lib/approvals.canDecide` mirrors `api/approvals._may_decide` to decide whether to show Approve/Deny, and the server still answers 403 if it is wrong. Navigation shows Audit only to auditors and org admins, and Policies explains itself to everyone else. A room you cannot see is "room not found" (decision 36), not an empty room.
117. **Room view** uses one WebSocket per room (`/v1/ws/rooms/{id}?after_seq=...`): it replays from the start, goes live, and on a reconnect resumes from the last message seen, so nothing is missed or shown twice. It is opened only once the room itself has loaded: for a room the person cannot see, the server refuses the handshake with an HTTP 403, which a browser reports as an anonymous failure (code 1006), and the socket would otherwise retry forever. Task cards refresh when a task-related message arrives and every 4 s. Mentions: the composer's `@` picker inserts `@handle`, and the message's `mentions` are the ids of members named in the text; the text is highlighted for recognised members only. "Send as task" adds a skill (suggested from the mentioned agents' registered skills).
118. **Inbox** reads `/v1/notifications` (newest first, "Load older" by cursor) and a live `/v1/ws/notifications` socket: a push updates the unread badge, refreshes the list and raises a toast (click to dismiss). Each row offers only what `actions` allows (open room, reply, cancel task, approve/deny), so a Risk person told about an Ops task sees the notice and the trace link but no room link.
119. **Agent health** is derived in the browser (`lib/format.agentHealth`) because there is no health endpoint: *ok* if the card was fetched within 2 hours (the hub refreshes hourly), *stale card* beyond that, *disabled*, and SDK agents (which have no card) show an *SDK* chip instead. Only admins of the owning department see the endpoint and the credentials flag (decision 57). Registration offers only the departments the person may register for.
120. **Trace viewer** renders `/v1/traces/{id}` as a tree with a chip per span kind, status, duration, the policy decision and reason, the approval and who must decide, and, on demand, the delegation chain (`/v1/delegations/{id}/chain`, root human first). Spans in rooms the viewer cannot read are counted ("N more are in rooms your department cannot see"), not shown.
121. **Policies:** a form per rule type builds the JSON (`lib/policy.buildRule`); the server validates and audits it. Existing rules can be switched off, edited as JSON or deleted. Org admins edit; auditors read; everyone else gets an explanation of the defaults.
122. **Browser tests are real.** `server/tests/e2e/test_browser_demo.py` runs the built app (`vite preview`) in headless Chromium against a live hub with the demo agents: three separate sessions play the whole story (mention picker, held task, live push, inline approval, live task cards, trace and delegation chain, inbox, registry, audit verify), and a second test covers department scoping, registering an agent by card URL (and a failed one), and the policy editor. They also assert that no uncaught page error occurs. They skip themselves if Node or Playwright's Chromium is missing (`SKIP_E2E=1` forces it). They found two real bugs that type-checking and unit tests could not: an effect that returned `scrollIntoView()`'s Promise (React treats a returned value as the cleanup, which crashed the whole app to a blank page in current Chromium), and the endless WebSocket retry above.
123. **Known limits:** no refresh token; no pagination of the rooms list or the message history (the room replays all of it over the socket); the room access section lists nothing (the API has no read endpoint for access rows, so it is grant-only); trace and audit pages are read-only views with no filtering or search; no mobile layout work beyond Tailwind's defaults; accessibility is basic (labels, roles and live regions on toasts) and has not been audited.

## Facade persistence, push notifications, signed artifacts

124. **The facade's state is in Postgres** (migration 0008). `facade_tasks` holds the SDK's task snapshot per A2A task id, owned by the caller and linked to the Setu task; it replaces the SDK's in-memory task store and the in-memory `(wire id -> Setu task)` map (supersedes the "does not survive a restart" part of decisions 86 and 94). `GetTask`, `ListTasks` and `CancelTask` therefore work after a restart. A snapshot still saying `working` for a Setu task that has since ended is reported with Setu's state. Handlers stay cached per (caller, callee) in memory; they hold no state of their own. An id already used by another caller is refused. Own store class rather than the SDK's `DatabaseTaskStore`, because that one creates its tables itself instead of through Alembic.
125. **Signed artifacts are a hub attestation.** When a result is stored, Setu signs `{iss, sub: agent id, task, room, artifact, trace, iat, sha256(parts)}` as an EdDSA (Ed25519) compact JWS (`app/core/signing.py`). The signature is in the `result` message body (`signature`) and in the A2A artifact's `metadata.setu.signature` through the facade. The public key is served unauthenticated at `/.well-known/jwks.json`; `setu_sdk.verify.verify_artifact` checks a signature against it (extra `setu-sdk[verify]`). It proves "this agent returned these parts through Setu in this task", not that the origin agent signed. The digest is SHA-256 over canonical JSON (sorted keys, no spaces, whole-number floats as integers, because protobuf structs turn every number into a float). `SIGNING_KEY` (base64url 32-byte seed) is required outside dev; dev uses a public placeholder, so dev signatures prove nothing. Not done: signing Agent Cards (A2A `signatures`), key rotation (the JWKS is a list, so a second key can be added later), and a UI badge.
126. **Push notifications (A2A webhooks) are offered on the facade only.** Cards now advertise `pushNotifications: true`. A caller registers a webhook in `SendMessage.configuration.taskPushNotificationConfig` or with the `*TaskPushNotificationConfig` methods; the a2a-sdk sends the task events to it. Configs live in `facade_push_configs`, scoped to the caller; the token and authentication credentials are Fernet-encrypted at rest. The URL goes through the same SSRF guard as agent URLs (`validate_agent_url`, same private-host rule), is checked when registered (JSON-RPC -32602 if unsafe) and again when delivering, and the client does not follow redirects. Delivery is the SDK's best-effort single attempt, no retry queue. Setu does not yet register webhooks with the remote agents it calls (outbound push); it keeps using streaming.

Not built from Band: attachments (Setu messages carry text and A2A parts, no file upload) and the room-list avatar stacks (the list API does not return members).
131. **Home is the landing page** (`#/` and `#/home`). It shows four tiles (active tasks, approvals waiting on the viewer, agents online, 7-day success rate), "Needs your attention" (pending approvals), recent rooms and the agents. It uses existing endpoints plus the analytics summary; no new server logic.
132. **Teams** (migration 0009: `teams`, `team_members`). A team is a named group of people and agents owned by one department. It is only a grouping: it grants no room access, no delegation, and no policy exception, so adding a member never widens what they can do. Anyone in the org can read teams (membership is not secret and the directory is org-wide); the admins of the owning department and org admins create, rename, delete and change members (admin-only endpoints). Members may come from any department of the org. "Add all to a room" is done by the web app through the ordinary `POST /v1/rooms/{id}/members`, one member at a time, so room rules apply to each person; people already in the room (409) are skipped and other failures are reported.
133. **Analytics** is `GET /v1/analytics/summary?days=1..90`, read-only, computed from `tasks`. Org admins and auditors see the whole org; everyone else sees tasks their own department asked for or ran (a cross-department task counts for both). It reports totals by state, success rate (completed / (completed + failed)), mean time to complete, tasks created per day (UTC, zero-filled; completed and failed are counted on the day the task was created), and the ten busiest agents. The page draws one series in the validated reference blue (columns for days, bars for agents) with a table view, values at the bar tips, and hover details; failures are shown as a number with a mark and a word, never color alone. Not built: per-skill breakdowns (the skill lives in the request message, not on the task), latency percentiles, and export.
134. **Contacts** lists every active person and agent of the org grouped by department with search and filters; it reads the existing participants directory. Not built: Sonar (cross-organization discovery; the spec says other organizations never talk).
